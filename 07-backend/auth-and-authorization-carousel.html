Chapter 01

Stateful vs. Stateless Auth

Before evaluating permissions, identity must be verified. How session state is stored defines horizontal scaling limits.

Session-Based

Stateful Auth

Server holds session state in DB or Redis. Every HTTP request forces a database lookup to validate identity. Harder to scale horizontally across multi-region clusters.

Token-Based

Stateless Auth

Server issues signed JWTs. Identity and claims are self-contained. Any server verifies token signatures locally without contacting a central session store.

Chapter 02

The Microservices Bottleneck

In a distributed architecture, every service needs to verify incoming user identity. Naive design destroys system performance.

Anti-Pattern

Network Hop Bottleneck

Booking and Upload services call Auth Service on EVERY single request to check token validity. Creates severe network latency, auth service bottlenecks, and single point of failure.

Production Pattern

Decoupled Local Verification

Services fetch the Auth public key once and verify JWT signatures in-memory. Zero network hops per request, sub-millisecond validation, and independent scaling.

Chapter 03

Symmetric vs. Asymmetric Keys

How tokens are cryptographically signed dictates key security and maintenance across independent teams and services.

HS256 Algorithm

Symmetric Keys

Uses ONE shared secret to sign AND verify. If 10 microservices verify tokens, all 10 must hold the secret. If one service is compromised, all services are breached.

RS256 Algorithm

Asymmetric Keys

Private key stays strictly on Auth Service to sign tokens. Microservices only receive the Public key to verify signatures locally without key leak risks.

OIDC & OAuth 2.0 Standards

Standardizing identity exchange stops teams from reinventing auth protocols. OIDC builds identity directly on OAuth 2.0.

1

Service Discovery Endpoint

Standardized GET /.well-known/openid-configuration exposes authorization_endpoint, userinfo_endpoint, and jwks_uri.

2

Single-Use Auth Code Exchange

User authenticates; provider redirects with a short-lived authorization code. Token is never exposed directly in browser URLs.

3

Server-to-Server Token Handshake

Backend exchanges code + client_secret at the provider token endpoint to securely receive identity claims.

Chapter 05

The Authorization Myth

Developers often assume Authorization is just checking string roles like "ADMIN". Real-world systems require far more nuance.

Naive Myth

Authorization = RBAC

Hardcoding string checks like if (user.role === 'ADMIN') crumbles when permissions branch orthogonally, roles become tenant-scoped, or access depends on resource relationships.

Architectural Reality

The Modern AuthZ Spectrum

Production systems evolve across 4 paradigms: Role-Based (RBAC) → Multi-Tenant Scoped Roles → Relationship-Based (ReBAC) → Attribute-Based (ABAC).

Chapter 06

RBAC & Breathing Space

RBAC groups permissions into roles. Numerical weight spacing simplifies hierarchy thresholds without breaking existing code.

ADMIN (Weight: 0) — Full System Access
SUB_ADMIN (Weight: 15) — Inserted with Breathing Space!
MANAGER (Weight: 30) — Operations & Management
USER (Weight: 70) — Standard Account Access

The Breathing Space Rule

Never allocate sequential integers (0, 1, 2). Leaving gaps (0, 30, 70) allows inserting new roles (15) without re-indexing database tables or rewriting comparison logic user.roleWeight <= 30.

Chapter 07

Multi-Tenant Scoped Auth

In B2B SaaS (GitHub, Slack, AWS), users have different roles per organization. Global role columns on user tables break completely.

Single-Tenant Flaw

Global User Roles

Storing users.role = 'ADMIN' grants global superuser power everywhere. It makes tenant isolation impossible in multi-org SaaS platforms.

Multi-Tenant Scoped

Scoped Role Mappings

Authorization is scoped via junction tables: user_org_roles and user_repo_roles. User Saif is an ADMIN in Org Chaicode, but a VIEWER in Org Acme.

Chapter 08

Relationship-Based Auth (ReBAC)

When permissions depend on nested graph relationships (Google Drive sharing, GitHub org repos), standard SQL joins break down.

A

Graph Traversal Evaluation

ReBAC checks reachability in a directed graph: "Is User Saif a MEMBER of Organization Chaicode?"

B

Inherited Transitive Access

Organization Chaicode is set as parent of Repository GenAI. Any user with member status on Org Chaicode automatically inherits Edit rights on Repo GenAI.

Google Zanzibar & Tuples

Google Zanzibar standardizes global authorization across billions of resources using lightweight, uniform Relation Tuples.

Universal Tuple Syntax

<object>#<relation>@<user / subject>
Org Membership Tuple

Direct User Relation

Expresses user membership in an org:

organization:chaicode#member@user:saif
Resource Parent Tuple

Inherited Object Relation

Expresses parent-child hierarchy:

repo:genai#parent@organization:chaicode

Chapter 10

Attribute-Based Access (ABAC)

Evaluates dynamic attributes across Subject, Resource, Action, and Environment at the exact moment of request execution.

Subject & Resource

Identity & Target

User Department == Document Department AND User Clearance Level >= Document Classification Level.

Action & Environment

Context & Constraints

Action == 'EDIT' AND Request Time is Business Hours (09:00 - 17:00) AND Connection is via Corporate VPN.

Chapter 11

Choosing Your Auth Stack

Match your authorization architecture to your system requirements and organizational scale.

Simple Monoliths

RBAC

Best for single-tenant apps with fixed user roles and internal management dashboards.

B2B SaaS

Scoped Multi-Tenant

Best for standard multi-organization SaaS requiring clear tenant isolation and org admins.

Collaborative SaaS

ReBAC / OpenFGA

Best for complex apps with nested sharing, org structures, and graph permissions (Drive, GitHub).

High Compliance

ABAC / OPA

Best for enterprise compliance, financial software, and location/VPN-restricted resources.
