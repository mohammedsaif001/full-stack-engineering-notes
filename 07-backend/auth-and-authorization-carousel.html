Step 01 • Authentication

Stateful Auth (Sessions)

Most backend applications start here. Identity is managed on the server using centralized session memory.

How It Works

Session Store Flow

When a user logs in, the server generates a random Session ID, stores session state inside Redis or PostgreSQL, and returns the Session ID in a set-cookie header. On every subsequent request, the server looks up the Session ID in the database.

The Bottleneck

Why Stateful Auth Fails at Scale

As user traffic scales and architectures transition into microservices, stateful authentication hits hard operational walls.

Per-Request DB Hit

Database Latency

Every single incoming API call forces a round-trip network lookup to the session database, turning Redis/DB into a hot central bottleneck.

Multi-Region Pain

Scaling Failure

Replicating stateful session stores synchronously across multi-region deployments or isolated microservices creates immense complexity.

Step 02 • The Fix

Stateless Auth (JWT Tokens)

To eliminate session database lookups, systems shift identity storage directly into self-contained cryptographic tokens.

The Stateless Evolution

Cryptographic Claims

The server signs a JWT containing user claims (User ID, Email, Expiry). Any receiving API server verifies the token signature locally using cryptography without touching a central database.

The Security Flaw

The Microservices Key Dilemma

Stateless JWTs solve database lookups, but naive implementations create severe microservices security risks.

Symmetric Keys (HS256)

Shared Secret Risk

Sharing 1 secret key across 10 microservices means if 1 service is breached, an attacker can forge tokens for all 10 services.

Central Check Hop

Auth Service Dependency

If microservices call the Auth service on every request to verify tokens, you re-introduce the exact network bottleneck you tried to solve.

Step 03 • Production AuthN

Asymmetric Keys & OIDC

Decoupled microservices identity is solved using Asymmetric Key Pairs (RS256) and OpenID Connect (OIDC) standards.

1

Private Key Signing

Auth Service keeps the Private Key secret and uses it to sign JWT tokens upon login.

2

OIDC Service Discovery & JWKS

Services fetch the Public Key from GET /.well-known/openid-configuration and cache it locally.

3

Local Zero-Trust Verification

Every microservice verifies signatures in-memory using the Public key with 0 network hops.

Step 04 • Authorization

Role-Based Access (RBAC)

Once identity is verified, we must check permissions. RBAC groups permissions into assigned roles (e.g. Admin, Manager, User).

ADMIN (Weight: 0) Full System Operations
SUB_ADMIN (Weight: 15) Inserted via Breathing Space
MANAGER (Weight: 30) Management Permissions
USER (Weight: 70) Standard Account Level

The Breathing Space Rule

Use numerical weight gaps (0, 30, 70) instead of sequential integers (0, 1, 2). This allows inserting new roles (15) without altering existing threshold code user.roleWeight <= 30.

The SaaS Limitation

Why Global RBAC Fails in SaaS

Storing a single role column on the user table works for simple monoliths, but completely breaks in B2B SaaS platforms.

The Global Role Flaw

Global Privilege Leak

Storing users.role = 'ADMIN' grants global superuser power everywhere. It makes multi-org tenancy impossible (e.g., Slack, GitHub, AWS).

Real-World SaaS Context

Multi-Tenant Requirement

User Saif must be an ADMIN in Organization , but only a VIEWER in Organization Acme Corp.

Step 05 • Tenant Scoping

Multi-Tenant Scoped Auth

To fix global role flaws, authorization logic must be scoped per organization and resource using junction tables.

Scoped Mapping Architecture

Junction Table Isolation

Roles are isolated per context: user_org_roles maps (user_id, org_id, role) and user_repo_roles maps (user_id, repo_id, role). Org admins automatically inherit cascaded access across child resources.

The Graph Complexity

Why Scoped RBAC Fails in Deep Graph Apps

As platforms add nested sharing (Google Drive folders, GitHub teams), multi-table SQL joins become impossible to maintain.

SQL Join Explosion

Query Performance Collapse

Evaluating access across nested folders, inherited teams, and public link shares requires 10+ table joins per request, destroying API response times.

Maintenance Nightmare

Hardcoded Logic Sprawl

Permission inheritance rules get duplicated across dozens of SQL queries, creating security holes and auditing nightmares.

Step 06 • Graph Permissions

ReBAC & Google Zanzibar

Google Zanzibar solves nested sharing by modeling permissions as graph reachability using uniform Relation Tuples.

Universal Relation Tuple Format <object>#<relation>@<user / subject>
Org Member Tuple

Expresses user org relation:

organization:myorg#member@user:saif
Inherited Parent Tuple

Expresses object inheritance:

repo:genai#parent@organization:myorg

The Contextual Limit

Why Static Graphs Aren't Enough

ReBAC graphs excel at relationship checks ("Is Saif a member of Org X?"), but fail when access depends on dynamic real-time context.

Static Relation Trap

Missing Dynamic Signals

ReBAC cannot natively check: "Is access allowed ONLY during business hours (09:00-17:00), from a Corporate VPN, in region EU-West?"

Attribute Explosion

Graph State Pollution

Trying to encode dynamic IP addresses, time slots, or document clearance levels into static graph tuples explodes graph storage.

Step 07 • Dynamic Context

Attribute-Based Access (ABAC)

ABAC evaluates real-time attributes across Subject, Resource, Action, and Environment at request execution time using Policy Engines (OPA).

Pillar 1: Subject & Resource

Identity & Target

User Department == Doc Department AND User Clearance Level >= Doc Classification.

Pillar 2: Action & Environment

Context & Constraints

Action == 'EDIT' AND Request Time <= 17:00 AND Connection is Corporate VPN.
