Step 01 • Identity

What is Authentication (AuthN)?

Before you give anyone a key to the house, you must confirm who is knocking at the front door. AuthN answers one fundamental question: "Who are you?"

Layman Analogy The Airport Security Checkpoint

When you arrive at airport security, you hand the officer your passport. They compare your face to the photo and confirm your name. They aren't asking if you bought first-class or economy yet; they are strictly verifying your real identity.

The Identity Proof

Credentials Handshake

The client supplies proof: email + password, OTP, or biometric passkey. The backend verifies against salted cryptographic hashes (Argon2 / Bcrypt).

The Verified Output

The Confirmed Identity

Once proven, the server outputs a verified claim: a User ID (e.g. usr_9812). This ID is the foundation for every subsequent request.

Senior Dev Rule
Authentication is binary: identity is proven (200 OK) or invalid (401 Unauthorized). It has zero knowledge of permissions or roles.

Step 02 • Sessions

Stateful Auth (Sessions)

Most backend systems start here. Identity is remembered on the server by storing active user sessions inside centralized server memory or a database.

Layman Analogy The Hotel Front Desk Register

When you check in, the front desk receptionist writes your name into their big guestbook and hands you a brass locker key #42. Every time you ask for room service, they walk to the desk and look up #42 in the guestbook to see who you are.

Client Side

Opaque Cookie

The client receives a random session string in an HttpOnly cookie (sid=sess_9f82d1a). The browser knows nothing about user details.

Server Side

Central Store (Redis)

The server keeps full user state (User ID, IP, created time, last active) inside memory cache, indexed by the session ID.

Why Developers Love It Early On
Instant revocation! To log a user out or ban an account, just run redis.del(sessionId). The session is destroyed immediately.

Step 02 • Under the Hood

The 3-Step Session Flow

How stateful authentication executes across every HTTP request cycle between browser, server, and session database.

1

Login & Session Creation

User submits credentials. Server verifies password, creates a random session ID, and writes user metadata into Redis or PostgreSQL.

2

Cookie Set in Browser

The server responds with Set-Cookie: sid=sess_9f82d1a; HttpOnly; Secure. The browser automatically stores and attaches it to future requests.

3

Database Lookup on Every Request

On every single API call, browser passes the cookie. The server executes a database query: "Does sid sess_9f82d1a exist in Redis and is it active?"

Notice the Inefficiency
Step 3 happens on every single HTTP request. If a user browses 50 pages, your session store handles 50 read queries just to check who they are!

The Bottleneck • Scale Limits

Why Sessions Fail at Scale (Part 1)

Stateful sessions work well for small monoliths. But as traffic surges and applications split, sessions hit harsh operational walls.

Bottleneck 01

Per-Request Database Hit

10,000 incoming requests per second forces 10,000 read queries on your session store every second. Redis or Postgres becomes a flaming bottleneck.

Bottleneck 02

Microservices Connection Sprawl

If Payment, Booking, and Chat services are separate microservices, all of them must maintain active connection pools to the central session store.

The Architectural Limit

The Single Point of Failure

If your central Redis session cache goes down or experiences memory pressure, every single service in your entire company goes down simultaneously.

The Fundamental Problem
The root cause is shared state. To scale horizontally, servers need to be stateless: verifying identity without querying any shared database.

The Bottleneck • Scale Limits

Why Sessions Fail at Scale (Part 2)

When your product expands to global multi-region deployments, centralized session storage breaks down completely.

Bottleneck 03

Multi-Region Replication Lag

If a user logs in via US-East, their session lives in US-East. When they hit edge servers in EU-West or Asia, cross-region replication lag creates session drops and 401 errors.

Bottleneck 04

Memory Exhaustion

Holding 10 million active concurrent sessions inside Redis RAM consumes massive cloud infrastructure dollars just to maintain idle user state.

Mental Model The Global Hotel Problem

Imagine checking in at a hotel in New York, but when you visit their London branch, the receptionist has to make an international phone call back to New York to check if your key is still valid!

Step 03 • Stateless Auth

Stateless Auth (JWT Tokens)

Instead of keeping session state on the server, what if the server gives the user a self-contained, cryptographically signed token? Enter the JSON Web Token (JWT).

Layman Analogy The Sealed Festival Wristband

Instead of checking the front desk register, the festival gives you a tamper-proof wristband stamped with a holographic seal. Any bouncer at any stage can glance at the holographic seal to verify it's authentic without calling the box office!

The Stateless Evolution

Self-Contained Cryptographic Proof

The token contains the user's identity and expiration time directly inside itself. Any receiving API server verifies the signature locally in memory in 0.1ms without touching a database.

Why Microservices Love It
Whether you have 2 servers or 2,000 servers across 5 continents, all of them can verify incoming JWTs independently without sharing a database.

Step 03 • Under the Hood

Anatomy of a JSON Web Token

A JWT is a compact, URL-safe string composed of three distinct base64url-encoded parts separated by dots.

The Structure

Three Parts Separated by Dots

header.payload.signature

1. Header (Red): Alg & Token type (e.g. {"alg": "RS256"}).

2. Payload (Blue): User claims (e.g. {"sub": "usr_123", "email": "saif@co.com", "exp": 1729000}).

3. Signature (Green): Cryptographic hash verifying the token hasn't been modified by 1 bit.

Critical Security Warning
JWTs are signed, NOT encrypted! Anyone can paste a JWT into jwt.io and read the payload. Never put passwords, API keys, or credit cards inside a JWT payload.

Step 04 • Security Challenge

The Stateless Paradox

If a JWT is stolen or compromised, how do you instantly cancel or "delete" it before its expiration time?

The Core Dilemma

The Client-Side Token Paradox

Because the token lives in the user's browser, you cannot reach into their machine and delete it. As long as the cryptographic signature is mathematically valid and exp > Date.now(), any server will accept it!

Strategy 01

Short-Lived Access + Refresh Token

Set Access Token expiry to 10 minutes. Issue a long-lived Refresh Token stored securely in your DB. If compromised, revoke the Refresh Token in DB; attacker access dies within 10 minutes max.

Trade-off
Strategy 1 is standard across the industry (Google, Auth0). But what if 10 minutes of attacker access is still too long for your compliance team?

Step 04 • Production Solutions

Instant Revocation in Production

Two battle-tested techniques to achieve instant 1-millisecond token invalidation without bringing back database lookup latency.

Strategy 02

Redis Deny-List (Blacklist) with TTL

When a user logs out, push the token's jti (Token ID) to Redis with a TTL matching its remaining life. Servers only check Redis for blacklisted IDs, keeping memory tiny.

Strategy 03 • Gold Standard

The User `token_version` Counter

Add token_version: 1 to your user table and include it in JWT claims. When a user clicks "Log out all devices" or changes password:

UPDATE users SET token_version = token_version + 1 WHERE id = 'usr_123';

If jwt.token_version < db.token_version, reject immediately! All previously issued tokens die in 1 millisecond globally.

Step 05 • Key Architecture

The Symmetric Key Vulnerability

In a monolith, 1 shared secret works. But in a distributed system with 20 microservices, naive symmetric encryption (HS256) is a disaster waiting to happen.

Symmetric Signing (HS256)

The Shared Secret Vulnerability

One secret key is used both to sign AND verify tokens. If you share this secret with 20 microservices, a breach in 1 low-priority service allows attackers to forge tokens for everything.

Layman Analogy The Master Key Maker

Imagine if every hotel cleaner, chef, and valet didn't just have room keys, but had the master machine that cuts new room keys! If one valet gets robbed, the thief can mint keys for every room in the hotel.

The Dilemma
We need a way for services to verify tokens without giving them the ability to create tokens.

Step 05 • The Fix

Asymmetric Keys (RS256)

Separate the power to sign tokens from the power to verify tokens using Public/Private Key Cryptography.

Layman Analogy The Royal Wax Seal & Stamp

The King keeps the physical metal wax stamp locked in his royal safe (Private Key). Everyone across the kingdom knows what the royal seal looks like (Public Key). Anyone can verify the seal on a decree, but nobody can forge a new one.

Private Key

Only on Auth Service

Used strictly to sign new JWTs upon login. Stays locked inside the Auth service; never leaves it.

Public Key

Shared with All Services

Used by Booking, Payment, and Chat services to verify signatures locally in 0.1ms with zero leak risk.

Zero Trust Achieved
Even if an attacker gains root access to your Chat service, they only steal the Public Key. They cannot forge or tamper with tokens.

Step 06 • Production Standards

OIDC & Automated Key Discovery

If public keys rotate periodically across dozens of services, how do we prevent hardcoding? We use OpenID Connect (OIDC).

The Standard Discovery Spec

The Well-Known Configuration Endpoint

Every OIDC-compliant provider exposes a standardized discovery JSON route:

GET /.well-known/openid-configuration

This returns the authoritative endpoints and the JWKS URI (JSON Web Key Set):

{ "issuer": "auth.co", "jwks_uri": "https://auth.co/.well-known/jwks.json" }
Automated Key Rotation

Zero Redeployments

Microservices fetch public keys from the JWKS URI once on startup, cache them in memory, and auto-refresh them when a key rotates without redeploying code.

Step 06 • Framework Clarity

OAuth 2.0 vs OpenID Connect

These two terms are constantly confused. Here is the definitive distinction every senior engineer knows.

Dimension OAuth 2.0 OpenID Connect (OIDC)
Core Purpose Authorization (Delegation) Authentication (Identity)
Question "What can this app access?" "Who is this user?"
Output Token Access Token (opaque or JWT) ID Token (JWT with user claims)
Analogy The Valet Key for a car Your State Driver's License
How They Relate
OIDC is built directly on top of OAuth 2.0. OAuth 2.0 handles the secure code-for-token redirect mechanics; OIDC adds the standardized user identity layer.

Step 07 • Pragmatic Engineering

The Dark Side: OIDC in Small Apps

Senior engineering is about picking the right tool for the job. Shoehorning enterprise OIDC into small applications is a major mistake.

Drawback 01

Massive Over-Engineering

Implementing redirect URIs, state parameters, PKCE challenges, code exchanges, and JWKS cache clients for an MVP with 2 developers turns simple signup into a nightmare.

Drawback 02

Network & Redirect Latency

Every login requires external browser redirects and backchannel HTTP requests between browser, backend, and provider, adding 400-800ms to user onboarding.

Mental Model The Enterprise Hammer

Using a full-blown OIDC suite for a small 1-database monolith is like hiring an armored bank truck with armed guards just to deliver a pizza down the street!

Step 07 • Pragmatic Choices

Vendor Costs & The Simpler Path

The hidden costs of third-party auth platforms and when to keep your architecture lean.

The Cost Trap

Monthly Active User Pricing

Outsourcing to OIDC providers (Auth0/Okta) starts free, but escalates drastically ($1,000s/mo for custom domains, enterprise SSO, and multi-tenancy as MAUs grow).

The Lean Alternative

HTTP-Only Cookie Sessions

For a monolith with 1 database and <50k users, secure HTTP-only cookie sessions or basic JWTs are 10x faster to build, simpler to debug, and free.

Engineering Wisdom
Don't adopt enterprise infrastructure until you have enterprise scale. Match your auth architecture to your team size and traffic.

Step 08 • The Great Split

Entering Authorization (AuthZ)

Now that we know who the user is, we face the second challenge: "What are they allowed to do?" This is Authorization (AuthZ).

Layman Analogy The Corporate Office Badge

Showing your badge to the front desk confirms you are Mohammed Saif, an employee (AuthN). But when you swipe your badge at the Server Room door, the electronic lock denies you entry because you don't have DevOps clearance (AuthZ).

Authentication (AuthN)

Identity Handshake

Checks credentials, proves identity, produces User ID. Happens once at the entrance.

Authorization (AuthZ)

Permission Enforcement

Checks roles and scopes. Evaluates a boolean (Allow/Deny) on every single action.

The Cardinal Rule
Never assume authentication implies permission. Just because someone holds a valid JWT token does not mean they have permission to delete a customer record.

Step 09 • Role Hierarchy

Role-Based Access Control (RBAC)

RBAC groups permissions into assigned roles. Instead of string checks, senior engineers use numeric pyramid weights.

The Naive Approach

String Equality Checks

if (role === 'ADMIN' || role === 'MANAGER')

Checks become repetitive and verbose. They don't reflect natural hierarchy: that an Admin inherently has all powers of a Manager.

The Senior Approach

Pyramid Numeric Weights

if (user.roleWeight <= RoleWeight.MANAGER)

Lower numbers represent higher privilege. A single inequality threshold cleanly checks entire tiers of permissions!

The Golden Question
Should you number roles as `0, 1, 2, 3`? Never. That brings us to the Breathing Space Rule on the next slide.

Step 09 • The 0 - 30 - 70 Law

The "Breathing Space" Rule

Why we use numerical weight gaps (0, 30, 70) instead of sequential integers (0, 1, 2, 3) in real-world systems.

0 ADMIN
Full System Operations & Billing
15 SUB_ADMIN
Inserted Later via Breathing Space!
30 MANAGER
Team Management & Approvals
70 STANDARD USER
Standard Read & Write Access
The Secret

Zero Code Refactoring

If you used sequential `0, 1, 2`, inserting `SUB_ADMIN` forces rewriting 50 controllers. With numeric gaps, `15` slips right between `0` and `30` without breaking existing code: roleWeight <= 30 automatically includes `15`!

Step 10 • The SaaS Dilemma

Why Global RBAC Breaks in SaaS

Storing a single role column on your users table works for simple monoliths, but explodes in modern B2B SaaS platforms.

The SaaS Reality The Multi-Organization Problem

Consider platforms like Slack, GitHub, or AWS: Saif is the ADMIN of his startup's GitHub Organization ("AlphaTech"), but is merely an outside CONTRIBUTOR or VIEWER in an open-source project ("AcmeCorp").

The Global Flaw

Global Privilege Leak

If you store user.role = 'ADMIN' globally, Saif becomes an Admin across every company on your entire platform. Single-tenant roles make multi-tenancy impossible.

Core Rule of Multi-Tenancy
A user has no role in isolation. A user only has a role within the context of a specific Organization or Workspace.

Step 10 • The SaaS Fix

Scoped RBAC Architecture

To support multi-tenancy, authorization logic must be scoped per tenant context using junction tables.

Org Scope

`user_org_roles`

Maps (user_id, org_id, role). Defines high-level company permissions (Owner, Billing Admin, Member).

Resource Scope

`user_repo_roles`

Maps (user_id, repo_id, role). Enables granular overrides for specific projects or repos.

Permission Cascading

Hierarchical Inheritance

Org admins automatically inherit access across all child repositories. External contractors only get added to specific user_repo_roles rows, isolating sensitive resources.

Step 11 • The Graph Crisis

When Scoped RBAC Collapses

Scoped tables solve simple Org roles. But what happens when products add Google Drive nested folders, Figma team sharing, or GitHub team hierarchies?

Mental Model The Russian Nesting Doll Problem

In a modern product, access isn't flat: User → Member of Backend Team → Team has access to Project → Project contains Folder → Folder contains File. Relational SQL was never designed to traverse deep graphs in real time.

Crisis 01

SQL JOIN Explosion

Checking permissions requires 8 to 12 recursive table joins on every click. Database CPU spikes to 100%.

Crisis 02

Sprawling Logic

Inheritance rules get hardcoded across dozens of SQL queries, creating audit and security nightmares.

Step 12 • Graph Authorization

ReBAC & Google Zanzibar

Google solved nested sharing with Zanzibar (powers Docs, Drive, YouTube, Cloud IAM). Permissions are modeled as graph reachability.

The Universal Formula

Relation Tuples

Instead of 50 junction tables, all permissions across all products are modeled as universal 3-part graph tuples:

<object>#<relation>@<user / subject>
Org Membership
org:acme#member@user:saif

Saif is directly a member of the Acme organization.

Inherited Parent
doc:roadmap#parent@org:acme

The roadmap document inherits permissions from Acme.

Zanzibar Core Insight
Checking access is simply asking: "Is there a path from User X to Resource Y in the graph?" Graph traversal completely replaces messy SQL joins.

Step 13 • Dynamic Context

Where ReBAC Fails: Enter ABAC

ReBAC graphs excel at static relationships ("Is Saif a member of Org X?"). But what happens when access depends on dynamic real-time conditions?

The Contextual Challenge When Graphs Cannot Express Context

"Allow wire transfers ONLY IF user belongs to Finance, during business hours (09:00 - 17:00), connected via Corporate VPN, with clearance >= 3, and transfer amount < $50,000."

The 4 Pillars of ABAC

Subject, Resource, Action, Environment

Evaluates user clearance, document status, action type, and real-time context (time of day, VPN, geolocation).

Policy Engines

Decoupled Rules with OPA

Rules are written declaratively in Rego (Open Policy Agent). The API sends JSON attributes; OPA returns Allow/Deny.

Senior Dev Summary
Start simple with sessions/JWTs. Scale to scoped RBAC for SaaS. Transition to ReBAC (Zanzibar) for nested sharing, and adopt ABAC for compliance and dynamic context!
